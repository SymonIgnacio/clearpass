# ClearPass System Audit Report (01/11)

## 1. Executive Summary

This audit evaluates the current state of the ClearPass Barangay Management System, covering frontend, backend, and database components. The system is built on a modern stack (React 18, Node 18, MySQL 8) and generally follows good architectural patterns. However, several critical alignment issues and inconsistencies were identified and addressed during this audit cycle.

**Key Achievements in this Cycle:**

- Fixed critical role ID mismatch preventing Admin access (ID 5 → 1).
- Restored missing database tables (`vehicles`, `visitors`) via remediation migration.
- Standardized Admin User creation to correctly map roles in the database.
- Implemented functional Resident Document Upload verification flow.
- Resolved database schema duplication (`audit_log` vs `audit_logs`).

## 2. Component-Specific Findings

### 2.1 Frontend (React/Vite)

- **Architecture:** Component-based architecture using Material UI. State management via Context API and local state.
- **Alignment:**
  - `roles.js` definition for Admin was `5`, but backend/DB expected `1`. **Status: Fixed.**
  - `ResidentSettings.jsx` used `FormData` correctly but backend endpoint path was mismatched (`/api/auth/submit-residency-verification` vs `/api/residents/verification/upload`). **Status: Fixed.**
- **Issues:**
  - `FormData` usage in some components bypasses the `apiRequest` utility, potentially missing standard error handling/interceptor logic.
  - Hardcoded API URLs in some components (e.g., `ResidentSettings.jsx` had fallback to `localhost:3001` while server runs on `3002`).

### 2.2 Backend (Node/Express)

- **Architecture:** Controller-Service-Repository pattern (lightweight). Centralized error handling and async wrappers.
- **Alignment:**
  - `adminController.js` was using `role_id` but the `users` table uses `role` column. **Status: Fixed.**
  - `residentController.js` missing document upload logic in `update` function. **Status: Fixed.**
  - Migration scripts (`migrate.js`) use CommonJS `require` syntax causing failures in ES Module environment. **Status: Pending (Workaround used).**
- **Security:**
  - Rate limiting enabled.
  - JWT Authentication active.
  - Role-based access control (RBAC) enforced on routes.

### 2.3 Database (MySQL 8)

- **Schema:**
  - `users` table uses `role` (int) linked to `roles` table.
  - Duplicate tables identified: `audit_log` (unused, empty) vs `audit_logs` (active). **Status: Fixed (Dropped `audit_log`).**
  - Missing tables `vehicles` and `visitors` referenced in code but missing in DB. **Status: Fixed.**
- **Consistency:**
  - Foreign key constraints generally present.
  - Charset/Collation: `utf8mb4_general_ci` (standard).

## 5. Recommendations

1.  **Standardize API Clients:** Refactor all direct `fetch`/`axios` calls in frontend pages to use the central `apiRequest` or `api.js` utility to ensure consistent token handling and error interception.
2.  **Fix Migration Scripts:** Rename `scripts/database/migrate.js` to `migrate.cjs` or rewrite with `import` syntax to support the project's ESM configuration.
3.  **Unified Constants:** Ensure a single source of truth for Role IDs and API Endpoints shared (or duplicated with strict sync) between frontend and backend to prevent drift.
4.  **Testing:** Add integration tests for critical flows (Resident Registration, Admin User Creation) to catch schema mismatches early.
