## Executive Summary

ClearPass has a broad feature surface (resident onboarding, document verification, certificates, blotter/case management, programs, analytics, admin tooling) but is currently at **high risk of authorization policy drift** and **inconsistent security posture** due to:

- **RBAC mapping mismatch** between documented roles in [System_requirements.md](file:///c:/xampp/htdocs/clearpass/System_requirements.md) and the role IDs/names used in the code and database.
- **Mixed routing architecture** (modular routes + “sharedRoutes” + legacy monolithic routes) mounted simultaneously, increasing the probability of duplicated endpoints and conflicting rules.
- **Access control gaps** in document request endpoints and legacy handlers (potential IDOR and PII exposure).
- **Dependency vulnerabilities** including a **critical** jsPDF issue in root dependencies and multiple **high** severity issues in server/client dependencies.

The system has good foundational controls (JWT auth, httpOnly cookies, helmet, xss-clean, rate limiting, some CSRF usage), but the above issues prevent confidently claiming compliance with the security and compliance requirements described in System_requirements.md.

## Findings (By Severity)

### Critical

#### CP-SEC-001: RBAC role mapping mismatch vs requirements (policy drift)
- Observed (UTC): 2026-01-10T22:04:33Z
- Impact: Incorrect allow/deny decisions across the system; impossible to assert compliance with System_requirements.md.
- Evidence:
  - Requirements define roles 1–6 with “Resident=4”, “Captain=5”, “Secretary=6” ([System_requirements.md](file:///c:/xampp/htdocs/clearpass/System_requirements.md#L1-L191))
  - Code uses: Admin=1, Captain=2, Secretary=3, Clerk=4, Blotter Officer=6, Resident=12 ([authMiddleware.js](file:///c:/xampp/htdocs/clearpass/server/middleware/authMiddleware.js#L21-L31), [roles.js](file:///c:/xampp/htdocs/clearpass/server/config/roles.js#L1-L26))
  - Client has mismatched role assumptions in places (e.g., role `5` treated as IT Admin in nav) ([permissions.js](file:///c:/xampp/htdocs/clearpass/client/src/utils/permissions.js#L184-L199))
- Recommendation:
  - Choose one authoritative role mapping (requirements doc vs DB vs code).
  - Implement a single source of truth and enforce it end-to-end:
    - DB seed/migrations for roles
    - JWT claims (`role` only, or `role_id` only)
    - Middleware normalization for both user role and allowed role sets
    - Client role constants and route guards.

#### CP-SEC-002: Document Requests endpoints allow potential IDOR/PII exposure
- Observed (UTC): 2026-01-10T22:04:33Z
- Impact: Residents may access or create requests for other residents; staff access may be unintentionally broad; potential privacy breach.
- Evidence:
  - `GET /api/documents/requests` branches on `req.user.role_id === 12` but tokens commonly carry `role` not `role_id` ([documentRoutes.js](file:///c:/xampp/htdocs/clearpass/server/routes/documentRoutes.js#L8-L34)).
  - `POST /api/documents/requests` accepts `resident_id` from request body without ownership enforcement ([documentRoutes.js](file:///c:/xampp/htdocs/clearpass/server/routes/documentRoutes.js#L36-L55)).
- Recommendation:
  - Standardize on `req.user.role` (single claim) and remove the `role_id` branch.
  - For residents, force `resident_id` to be derived from `req.user.resident_id` and ignore body `resident_id`.
  - Restrict staff listing to appropriate roles (`admin`, `secretary`, `clerk`) rather than “any non-resident”.

#### CP-SEC-003: Critical dependency vulnerability in jsPDF (root)
- Observed (UTC): 2026-01-10T22:04:33Z
- Impact: Potential local file inclusion / path traversal in PDF generation paths if untrusted inputs are used.
- Evidence: Root audit output indicates `jspdf <=3.0.4` critical vulnerability (GHSA-f8cm-6447-x5h2).
- Recommendation:
  - Upgrade jsPDF to a fixed version (audit suggests `jspdf@4.0.0` is breaking; schedule compatibility testing).
  - Add input hardening around any file-path-like parameters passed to PDF generation.

### High

#### CP-SEC-004: Legacy router + modular router both mounted at `/api` (duplication/conflicts)
- Observed (UTC): 2026-01-10T22:04:33Z
- Impact: Conflicting authorization rules, inconsistent response schema, difficult security auditing, accidental exposure.
- Evidence:
  - Modular mounts in [index.js](file:///c:/xampp/htdocs/clearpass/server/index.js#L167-L203)
  - Shared legacy routes: [sharedRoutes.js](file:///c:/xampp/htdocs/clearpass/server/routes/sharedRoutes.js) mounted at `/api` ([index.js](file:///c:/xampp/htdocs/clearpass/server/index.js#L191-L196))
  - Monolithic routes: [routes.js](file:///c:/xampp/htdocs/clearpass/server/routes.js) mounted at `/api` ([index.js](file:///c:/xampp/htdocs/clearpass/server/index.js#L194-L200))
- Recommendation:
  - Deprecate the legacy monolithic router and ensure all functionality exists in modular routes.
  - Add route tests that assert a single handler per path/method and consistent middleware chain.

#### CP-SEC-005: High-severity server dependency vulnerabilities (xlsx, qs)
- Observed (UTC): 2026-01-10T22:04:33Z
- Evidence: `npm audit` in server reports:
  - `xlsx` high severity prototype pollution / ReDoS with “No fix available”.
  - `qs` high severity DoS memory exhaustion (fix available).
- Recommendation:
  - Replace `xlsx` dependency or sandbox its usage (validate and cap workbook sizes; avoid parsing attacker-controlled XLSX).
  - Patch `qs` via `npm audit fix` (verify Express/body-parser compatibility).

#### CP-SEC-006: Client dependency vulnerabilities in react-router and @remix-run/router
- Observed (UTC): 2026-01-10T22:04:33Z
- Evidence: `npm audit` in client reports high severity XSS open-redirect vulnerabilities.
- Recommendation:
  - Upgrade `react-router-dom` / `react-router` to patched versions.
  - Ensure all redirects use allow-listed internal routes; avoid using untrusted query strings to redirect.

### Medium

#### CP-SEC-007: Partial CSRF coverage despite cookie-based auth
- Observed (UTC): 2026-01-10T22:04:33Z
- Impact: Some state-changing routes may be CSRFable since authentication uses cookies.
- Evidence:
  - CSRF applied only to certain prefixes in [index.js](file:///c:/xampp/htdocs/clearpass/server/index.js#L126-L132).
  - Many write endpoints exist outside those prefixes (e.g. `/api/resident-auth/*`, `/api/announcements`).
- Recommendation:
  - Apply CSRF to all cookie-auth state-changing endpoints (POST/PUT/DELETE), with explicit allow-lists for token-based clients if needed.
  - Add integration tests that ensure a missing CSRF token fails for cookie-auth flows.

#### CP-SEC-008: Uploads stored unencrypted on disk (non-compliance)
- Observed (UTC): 2026-01-10T22:04:33Z
- Impact: Non-compliance with “documents encrypted and stored securely”; higher breach impact.
- Evidence:
  - Disk storage under `server/uploads/documents` via multer diskStorage ([upload.js](file:///c:/xampp/htdocs/clearpass/server/middleware/upload.js#L1-L44)).
- Recommendation:
  - Store documents encrypted-at-rest (e.g., envelope encryption with KMS or AES-GCM + key rotation policy).
  - Restrict file system permissions and implement retention + disposal policies.

#### CP-SEC-009: Error/response schema inconsistencies across routes
- Observed (UTC): 2026-01-10T22:04:33Z
- Impact: Clients may mishandle errors; logging/audit could miss events.
- Evidence:
  - Standard error handler: [errorHandler.js](file:///c:/xampp/htdocs/clearpass/server/middleware/errorHandler.js)
  - Alternate error handler exists: [monitoring.js](file:///c:/xampp/htdocs/clearpass/server/monitoring.js#L304-L344)
  - Routes commonly return ad-hoc `{error:'...'}` or `{message:'...'}`.
- Recommendation:
  - Standardize API response envelopes (success/data/error) and enforce via middleware helper functions.

## Compliance Status vs System_requirements.md

Overall: **Partially Compliant** (significant gaps for RBAC correctness and document encryption/retention).

### Role Mapping Compliance
- Documented role IDs (1–6) do not match the system’s effective roles (Admin=1, Captain=2, Secretary=3, Clerk=4, Blotter Officer=6, Resident=12).
- This blocks a compliant RBAC verification until mapping is reconciled.

### Requirements Coverage Highlights
- Open registration: Present (resident open register endpoints + UI), but controls around storage encryption/retention are missing.
- Document verification: Present (secretary document verification flows), but “documents encrypted” is not implemented.
- Captain read-only: Present in backend via `enforceReadOnly`, but client role mapping inconsistencies may show/hide the wrong UI.
- Secretary restrictions: “Cannot access system configuration” is partially enforced (routes exist under `/api/system-admin`, but role checks must be validated end-to-end given role mismatches).

## Recommendations Roadmap (Prioritized)

1. Unify RBAC mapping and JWT claims across DB/server/client (Critical).
2. Remove or quarantine legacy `/api` monolithic routes to eliminate duplicate handlers (High).
3. Fix document request ownership enforcement and staff visibility (Critical).
4. Apply CSRF to all cookie-auth state-changing endpoints (Medium).
5. Replace/patch vulnerable dependencies (Critical/High).
6. Implement encrypted document storage + retention/disposal policies (Medium).
7. Add automated RBAC regression tests and endpoint policy snapshots (High).
8. Improve accessibility (dialogs, focus trapping, aria labels) and responsive layout (Low/Medium).
